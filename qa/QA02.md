# QA Track, Lesson 2 — Designing Test Cases
*v1.0.0*

**Goal for today:** learn the four test-design techniques that do most of the real work — equivalence partitioning, boundary values, decision tables, state transitions — and use each of them at least once to build a written suite for your feature area. By end of day `cases/` holds 20-ish cases that a stranger could execute without asking you a single question.

**Time budget:** ~85 min hands-on, ~20 min journal, ~15 min slack.

## 2. What a test case is (~15 min)

A test case is an instruction for producing a specific observation. Six fields, no more:

| Field | What goes in it |
|-------|-----------------|
| **ID** | `CART-01`. Stable, referenceable in a bug report or a chat message. |
| **Title** | One line, states the behavior: *"Cart total updates when quantity increases."* |
| **Priority** | P1 / P2 / P3. Derived from the risk list, not from vibes. |
| **Preconditions** | The state the world must be in before step 1. *"Logged in as customer, cart empty."* |
| **Steps** | Numbered, each one action. Concrete values, not "enter a quantity." |
| **Expected result** | What you will observe if the software is correct. One clear, checkable statement. |

Write one now, in `cases/cart-checkout.md`:

```markdown
### CART-01 — Cart total updates when quantity increases
**Priority:** P1
**Preconditions:** Logged in as customer@practicesoftwaretesting.com; cart empty.
**Steps:**
1. Open the catalog, open "Combination Pliers", note the unit price P.
2. Click "Add to cart".
3. Open the cart.
4. Set quantity to 3.
**Expected:** Line total reads 3 × P, and the cart subtotal equals the line total.
```

Four rules that separate a case from a wish:

- **A case must be able to fail.** "Verify the cart works" cannot fail — there's no observation in it. If you can't imagine writing "actual: X" underneath, it isn't a case.
- **Concrete values.** "Set quantity to 3" and "note the unit price P" beat "add some items." A case with vague inputs produces vague bugs.
- **One behavior per case.** A 30-step case that walks the whole app is not thorough, it's fragile: it fails at step 4 and the other 26 steps go unexecuted forever. Long chains hide bugs behind earlier bugs.
- **Preconditions are part of the case.** Half of all "cannot reproduce" bounces are a missing precondition. *Logged in as whom? Cart in what state?*

## 3. Equivalence partitioning (~15 min)

The quantity field accepts... what, exactly? You can't try every value, so split the input space into groups where you believe every member behaves the same, and test **one representative from each group**. That's equivalence partitioning, and it's the technique that turns infinity into six cases.

For the cart quantity field, a plausible partitioning:

| Partition | Representative | Valid? |
|-----------|----------------|--------|
| Positive integer within stock | `3` | valid |
| Zero | `0` | invalid |
| Negative | `-1` | invalid |
| Non-integer | `1.5` | invalid |
| Non-numeric text | `abc` | invalid |
| Empty | `` | invalid |
| Absurdly large | `99999` | invalid (probably) |

Seven cases instead of infinity. The technique's whole load-bearing assumption is the phrase *"you believe every member behaves the same."* That belief is sometimes wrong — that's precisely what boundary testing (next section) is for.

**Note the asymmetry:** one representative is enough for the valid partition, but you generally want *each* invalid partition tested separately, because invalid inputs get handled by different code paths — a type check, a range check, a required-field check. They fail differently, so they get their own cases.

Do it for real. Pick two more input fields in your feature area — a checkout address field, the search box, the price filter — and partition them in your notes before you write cases.

## 4. Boundary value analysis (~15 min)

Bugs cluster at edges. `>` written where `>=` was meant, an array indexed one past its end, a field that allows 10 characters and a database column that stores 8. Almost none of those show up at "3"; all of them show up at the boundary.

So for every partition boundary, test **the value on each side of the line, and the line itself**. If valid quantity is 1 to stock:

- `0` (just below), `1` (the boundary), `2` (just inside)
- `stock-1`, `stock`, `stock+1`

Find a real product's stock level in the Toolshop and use the actual number. If the UI doesn't show stock, that itself is a finding — write it in your `## Questions` list, because *you cannot test a boundary you can't see.*

Boundaries hide in less obvious places than number fields:

- **Text length** — a 1-character name, a 255-character name, a 256-character one.
- **Time** — the moment a session expires. (The Toolshop's API tokens are short-lived; Lesson 6 will make you care.)
- **Collections** — an empty cart, a cart with one item, a cart with enough items to paginate.
- **Money** — the cheapest product in the catalog and the most expensive, in the same cart.

Add boundary cases for your feature area. They're usually the highest-yield cases in a suite and they're rarely the ones people write first.

## 5. Decision tables (~15 min)

Some behavior depends on a *combination* of conditions, not one input. Enumerating those in prose guarantees you'll miss a row. Use a table.

The Toolshop's checkout offers several payment methods, and each one asks for different fields. That's a decision table:

| # | Payment method | Required fields present? | Logged in? | Expected |
|---|---------------|--------------------------|-----------|----------|
| 1 | Credit card | yes | yes | Order placed, confirmation shown |
| 2 | Credit card | no (card number blank) | yes | Validation error, no order created |
| 3 | Bank transfer | yes | yes | Order placed |
| 4 | Gift card | yes | yes | Order placed |
| 5 | Credit card | yes | no | Prompted to log in before payment |

Go to the checkout and read the actual options and their actual fields — don't trust my table, it's an example and the app changes. Build yours from what's on screen, then write one test case per row.

Two disciplines here:

- **The table is the audit trail.** When someone asks "did you test gift card with a missing field," you point at a row instead of trying to remember.
- **Full enumeration explodes.** Five conditions with three options each is 243 combinations. When it explodes, you drop to *pairwise*: cover every pair of values at least once rather than every combination. It's a known technique with tools that generate the set for you; you don't need it today, but know the word — it's the standard answer to "we can't test all combinations."

## 6. State transitions (~10 min)

A cart is not a set of fields, it's a **state machine**: empty → has items → checkout started → address entered → payment entered → order placed. Some transitions are allowed, some are not, and the interesting bugs live in the ones nobody thought about.

Sketch the states and arrows in `cases/state-notes.md` — boxes and arrows in plain text is fine. Then hunt for the transitions the developer probably didn't consider:

- Start checkout, then hit the **browser back button** and change the cart. What does the order total use?
- Start checkout, open the app in a **second tab**, empty the cart there, and finish paying in the first tab.
- Log out **mid-checkout**. Log back in. Is the cart still there? Should it be?
- Place an order, then hit **back** and press the pay button again. Two orders?

These are the cases that separate testers from clickers. Every one of them is a legal sequence of user actions, and every one of them skips a step the happy path guarantees. Write at least three as proper cases with preconditions and expected results — and be careful with the expected results here, because the honest answer is sometimes *"I don't know what should happen, and that's a question for the product owner."* Write that down as the expected result. **"Unspecified — needs a decision" is a legitimate, valuable finding.**

## 7. Build the suite (~15 min)

Finish `cases/cart-checkout.md`. Target ~20 cases, ordered by priority, covering:

- at least 3 from **equivalence partitioning** (mark them `[EP]`)
- at least 4 from **boundary analysis** (`[BVA]`)
- at least 4 from a **decision table** (`[DT]`)
- at least 3 from **state transitions** (`[ST]`)
- the rest: the plain happy paths, which still need to exist

Tag each case with the technique. In Lesson 5 you'll ask Claude for gaps, and the tags will show you *which kind of thinking* you're weakest at — which is more useful than the count.

Do **not** execute them today. Writing and running are different modes; mixing them means you stop designing the moment you find your first bug. Tomorrow is execution day.
