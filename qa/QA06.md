# QA Track, Lesson 6 — Claude Code as a QA Engineer
*v1.0.0*

**Goal for today:** turn the smoke suite you timed in Lesson 4 into automated browser tests, using Claude Code to write most of them and your judgment to review every line — then put them in CI so they run without you. By end of day: green tests, a deliberate red one, a GitHub Actions run, and an honest list of what stayed manual.

**Time budget:** ~95 min hands-on, ~25 min journal.

Rules are the Week 4 rules, unchanged: **review every diff before accepting; never approve a command you can't explain; if it writes a line you don't understand, ask about that line before you commit it.** One addition, in section 6, that's specific to test code and matters more than the rest.

```

```

## 2. Write the first test yourself (~20 min)

Same principle as W05D1: you write the first one, by hand, so you have a standard to judge the rest against.

```
subl tests/test_smoke.py
```

```python
BASE = "https://practicesoftwaretesting.com"


def test_smoke_01_home_page_lists_products(page):
    page.goto(BASE)
    # Playwright waits for the locator to appear — no sleeps.
    assert page.get_by_role("link").count() > 0
```

Run it:

```
pytest -v
```

That test is deliberately weak — it proves the harness works and almost nothing else. Now make it real. Open the Toolshop in Chrome, open DevTools, and **inspect the elements you need**. This app tags its controls with `data-test` attributes; find the ones for the search box and the product grid and use them:

```python
def test_smoke_01_search_returns_matching_products(page):
    page.goto(BASE)
    page.get_by_test_id("search-query").fill("hammer")     # confirm the real id in DevTools
    page.get_by_test_id("search-submit").click()
    results = page.get_by_test_id("product-name")
    assert results.count() > 0
    assert "hammer" in results.first.inner_text().lower()
```

Two things to internalize while you're in here:

- **Selector choice is the whole maintenance story.** A test that finds a button by its CSS class breaks the day someone restyles it. `data-test` attributes exist precisely so tests can hold onto something the designer won't move. Prefer, in order: `data-test` ids → accessible role and name (`get_by_role("button", name="Add to cart")`) → visible text → CSS. Never an XPath copied out of DevTools; those are the definition of brittle.
- **Never `sleep()`.** Playwright's locators wait for the element on their own. A `time.sleep(2)` is how a suite becomes both slow *and* flaky — flaky because two seconds is always too few on the one machine that matters.

## 3. Hand the rest to Claude Code (~20 min)

Start Claude Code in `~/dev/qa-lab`. Give it the standard *and* the facts:

> This repo automates a manual smoke suite against https://practicesoftwaretesting.com
> (an Angular demo store). `tests/test_smoke.py` has one test I wrote by hand — match
> its style. `cases/smoke.md` lists the manual cases.
>
> Write the remaining smoke tests, one test function per case, named after the case ID.
> Constraints:
> - Use `data-test` attributes for selectors where they exist; role/name if not. No XPath.
> - No `sleep()`. Use Playwright's built-in waiting.
> - Every test must have an assertion that could actually fail.
> - Do not invent selectors. If you don't know a selector, leave a `# TODO: confirm
>   selector` comment rather than guessing.
>
> Start with SMK-02 only. Show me the diff before writing anything else.

One case at a time, on purpose. A ten-test diff is a diff you'll skim, and skimming is how unreviewed code enters your repo wearing a lab coat.

For each diff, three questions before you accept:

1. **Does the assertion match the manual case's expected result?** This is where generated tests drift: your case said "the line total equals 3 × unit price," the test asserts the page contains the text "Combination Pliers." Both pass. Only one is your test.
2. **Could this test fail?** `assert page.url is not None` cannot. Neither can a test whose only assertion is that a page loaded. Hunt these — they're the most common defect in generated test code, and they're invisible because everything is green.
3. **Where did that selector come from?** If it isn't a `data-test` id you can find in DevTools, it's a guess. Check it, or make it a TODO.

Work through the suite until the smoke cases are covered. Run `pytest -v` after every accepted test, not at the end.

## 4. Green → red → green (~10 min)

A passing suite you've never seen fail proves nothing — Week 5's lesson, and it applies harder to code you didn't write.

Pick one test. Change its expectation to something false (assert the search for "hammer" returns *zero* results). Run it. Read the failure output: which test, which assertion, actual vs expected. Then put it back and confirm green.

Do the same for a *selector*: change one `data-test` id to a name that doesn't exist. That failure looks completely different — a timeout, waiting for an element that never appears. Learn to recognize both shapes now, because at 8am on a release morning you'll be reading one of them and deciding whether to hold the release.

## 5. Wire it into CI (~15 min)

Same machinery as Week 10 and Week 12 — GitHub Actions. Ask Claude Code:

> Add a GitHub Actions workflow that runs this suite on every push to main and once
> a day on a schedule. Install Playwright's chromium browser, run pytest, and upload
> screenshots/traces on failure. Show me the file before writing it.

Review it yourself before accepting. Three things to check, because generated workflow files are usually *nearly* right:

- **The trigger.** `on: push` plus a `schedule:` cron. Remember the cron runs in UTC — if the timing matters, do the conversion yourself. (You've been bitten by this before.)
- **The browser install step.** Missing `playwright install --with-deps chromium` is the single most common reason a suite that's green locally is red in CI. Linux runners need the system libraries too.
- **Failure artifacts.** A CI failure with no screenshot and no trace is a mystery you can't investigate. `--tracing=retain-on-failure` plus an upload step turns it into a file you can open.

Push, watch the run, and make it fail on purpose once so you see a red CI run and can open the artifact.

One courtesy: you're scheduling requests at somebody's free demo server. **Once a day, not every five minutes.**

## 6. The rule that only applies to test code (~10 min)

The suite goes red. You ask Claude Code to fix it. There are two ways to make a red test green, and only one of them is correct:

- Fix the **application** — but you don't own this app, so on this project, not available.
- Fix the **test** — if the test was wrong.
- **Weaken the assertion** until it passes.

That third one is fast, always works, and is almost always what an agent will reach for if you say "make the tests pass." It will change `assert count == 3` to `assert count >= 0`, or wrap the whole thing in a try/except, and report success. Nothing lied to you: the tests do pass.

So the rule: **a failing test is a question, not a task.** The question is *"has the application changed, or was my expectation wrong?"* — and only you can answer it, because only you know what the manual case was checking. Ask Claude Code to *diagnose*: read the failure, look at the trace, tell you what the page actually contained. Then you decide whether the assertion changes.

Practise it once. Break something so a test fails, then ask:

> This test is failing. Do not change any assertion. Tell me what the page actually
> showed and what the most likely cause is.

Compare that answer to what you get from "fix the failing test." Write both down — that contrast is your journal entry, and it's the most transferable thing in this lesson.

## Where to go from here

You've covered the spine: plan, design, execute, explore, report, regress, automate. What's next, roughly in order of usefulness:

- **API testing.** The Toolshop has one at `api.practicesoftwaretesting.com` — the same design techniques apply to request payloads, and the tests are ten times faster than browser tests. This is the highest-value next step: most of your smoke suite could arguably live at that layer instead.
- **Accessibility.** Keyboard-only navigation, screen readers, contrast. A large, under-tested surface with real legal weight.
- **Performance testing** — a genuinely different discipline. Never against somebody's free demo server.
- **The vocabulary.** The ISTQB Foundation syllabus is dry, and knowing its terms means you speak the language your future colleagues use in reviews.
- **Exploratory depth.** Elisabeth Hendrickson's *Explore It!* is the practical book; Bach and Bolton's writing on session-based test management is where the charter format in Lesson 3 comes from.
