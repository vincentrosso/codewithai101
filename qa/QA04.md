## 1. Why regression happens at all (~10 min)

You fixed a bug in the cart. Two weeks later the cart is broken again — differently, and in a place nobody touched.

That's a **regression**: working behavior that stopped working. It isn't carelessness, it's structural. Software is a pile of shared assumptions, and a change made in one place breaks an assumption held somewhere the author never read. You already met this in Week 5 of the main course — the diff looked fine, `canonical` went `None`, and nobody knew when. The tests were the answer then, and they're the answer now; the only new problem is *scale*. You can't re-run 200 manual cases every time someone merges a branch.

So testing gets sorted into levels, by what each one is for:

| Level | Question it answers | Typical size | When |
|-------|--------------------|--------------|------|
| **Smoke** | Is this build worth testing at all? | 5–15 cases | Every build |
| **Sanity** | Did the specific thing that changed work? | narrow, targeted | After a fix |
| **Regression** | Did anything that used to work stop? | the whole suite | Before a release |
| **Acceptance** | Does this do what the business asked for? | user-journey shaped | Sign-off |

The words get used sloppily in the wild. What matters is the distinction underneath: *smoke is broad and shallow, sanity is narrow and deep, regression is broad and deep and expensive.*

## 2. Build the smoke suite (~20 min)

A smoke suite answers one question — **is this build fundamentally alive?** — and it has to be cheap enough that you'll actually run it every time. If it takes 45 minutes, nobody runs it, and a suite nobody runs has a value of zero regardless of its coverage.

Go through `cases/cart-checkout.md` and tag cases `[SMOKE]`. Rules for the tag:

- **Breadth over depth.** One case per critical path, not five variations of one path. Log in, find a product, add to cart, check out, see the order. That's the spine.
- **Only the things that make everything else pointless.** If login is broken, your 40 cart cases can't run anyway. Login goes in. The cart quantity boundary at `stock+1` does not.
- **P1 only.** If it isn't P1 in your risk-derived priority, it isn't smoke.
- **Ten cases, hard cap.** The constraint is the design. If you have twelve candidates, cutting two is the exercise.

Write the list to `cases/smoke.md` as an ordered checklist — ordered so that the earliest failure kills the run fastest. There's no point checking the order confirmation page if login already failed.

## 3. Time it (~15 min)

Start a stopwatch. Run the smoke suite manually, start to finish, recording results. Stop the clock.

Write the number down. Then do arithmetic that almost nobody does:

```
Manual smoke pass:            ___ minutes
Releases per week:            ___  (assume 5 — one per working day)
Weeks per year:                48
Annual cost:  ___ × ___ × 48 = ___ minutes = ___ hours
```

At 12 minutes a pass and one release a day, that's about 48 hours a year of a human being clicking through a login form. That number is the entire business case for automation, and it's why Lesson 6 exists. It's also the number to bring to the argument when someone says automation isn't worth the time.

But note what the arithmetic does *not* say. It doesn't say automate everything.

## 4. What should never be automated (~10 min)

Automation is code. Code has to be written, reviewed, run, and — the part everybody forgets — **maintained**. Every automated test is a small permanent liability you've taken on in exchange for a repeated saving. When the saving doesn't beat the liability, don't.

Poor candidates:

- **Anything you'll run once.** A one-off migration check. Just do it by hand.
- **Anything still being redesigned.** Automating a UI that changes weekly means rewriting the test weekly. Wait for it to settle.
- **Judgment.** Is this layout confusing? Does this error message make sense to a human? Is this colour contrast acceptable to a person who's actually colour-blind? A machine can check contrast *ratios*; it cannot tell you the flow is bewildering.
- **Exploration.** By definition. A script only asks yesterday's questions.
- **The unstable.** A test that fails randomly is worse than no test at all — and it earns its own section.

Good candidates: stable, repeated, deterministic, with a clear pass/fail, on a path where a failure genuinely matters. Your smoke suite, in other words. That's not a coincidence.

### Flaky tests

A **flaky** test passes and fails on the same code. Usually a timing problem — the test checked before the page finished — sometimes shared state between tests, sometimes a real intermittent bug.

Flakes are toxic beyond their own result. Once a suite fails 5% of the time for no reason, humans start re-running it until it's green, and the day it fails for a *real* reason, they re-run it and ship anyway. A flaky suite doesn't just lose value, it trains people to ignore failures. Fix it or delete it; there is no third option, and "everyone knows that one is flaky" is how outages happen.

## 5. Risk-based selection, and the coverage lie (~10 min)

For a release you rarely get to run everything. So which cases?

Not "the ones that failed last time," not "all of them, quickly." Select by **what changed × what it would cost to be wrong**:

1. What areas did this release actually touch? (Read the changelog, or ask.)
2. What talks to those areas — shared code, shared data, the same screens?
3. Which of those is highest on `plan/risks.md`?

That's your regression selection, and it changes every release. Write down the selection *and the reasoning*, because "we ran the cart cases because the release touched pricing" is a defensible answer and "we ran the cart cases because they were at the top of the file" isn't.

And a warning about numbers: **coverage metrics measure execution, not thought.** Line coverage says a line ran during a test. It doesn't say the test asserted anything about it, and it says nothing about the case you never wrote. 100% coverage of your own suite means only that you executed everything you happened to think of. The bug you're going to ship lives in the part you didn't imagine — which is why exploration (Lesson 3) never goes away, no matter how green the dashboard is.

## 6. The release-readiness page (~15 min)

The deliverable of a test cycle isn't a bug count. It's a recommendation with the evidence attached. Write `plan/release-readiness.md`:

```markdown
# Release readiness — cart & checkout — YYYY-MM-DD

## Recommendation
Ship / Ship with known issues / Do not ship — one sentence of why.

## What I tested
Smoke: 10/10 executed, 9 pass, 1 fail (BUG-002).
Full suite: 18/24 executed. Selection rationale: <what changed and why these>.

## Open issues
| ID | Title | Severity | Priority | Status |
|----|-------|----------|----------|--------|
| BUG-001 | ... | Major | P2 | Open |

## What I did NOT test
- Admin area (out of scope, plan §2)
- Browsers other than Chrome
- CART-11, CART-14 — not run, out of time

## Risks I'm accepting by recommending this
Two or three sentences, named and specific.
```

That last section is what makes it a professional document instead of a status update. You are not the person who decides to ship — you're the person who makes sure the decision is made with open eyes. Writing the accepted risk down is how you do that, and it is also, bluntly, how you stay employed when one of them lands.

## 7. Automation shortlist (~10 min)

Add `plan/automation-candidates.md`. For each smoke case, score it:

| Case | Runs per year | Manual min | Stable UI? | Deterministic? | Automate? |
|------|---------------|-----------|-----------|----------------|-----------|
| SMK-01 login | 240 | 1 | yes | yes | **yes** |
| SMK-04 add to cart | 240 | 2 | yes | yes | **yes** |
| SMK-09 order confirmation email | 240 | 3 | n/a | no — no mail access | no, note as gap |

Rank them. The top of that list is exactly what you'll build with Claude Code in Lesson 6 — so be honest now, because you're the one who'll be maintaining it.
