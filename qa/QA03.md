# QA Track, Lesson 3 — Execution, Exploration, and the Bug Report
*v1.0.0*

**Goal for today:** run the suite you designed, then do a real time-boxed exploratory session where the suite ends and your judgment begins — and turn what you find into bug reports a developer can act on without asking you anything. By end of day: an execution log, a charter with notes, and three filed bugs.

**Time budget:** ~90 min hands-on, ~20 min journal, ~10 min slack.

Still no AI. Today is the day you learn what your own eyes catch.

---

## 1. Execute the suite (~25 min)

Open `cases/cart-checkout.md` and work top-down, highest priority first. For each case, record a result. Add a log at `cases/run-2026-xx-xx.md`:

```markdown
# Execution log — cart & checkout — YYYY-MM-DD
Build/env: practicesoftwaretesting.com, Chrome <version>

| Case | Result | Note |
|------|--------|------|
| CART-01 | PASS | |
| CART-02 | FAIL | see BUG-001 |
| CART-07 | BLOCKED | stock level not visible in UI, can't test upper boundary |
| CART-11 | NOT RUN | out of time |
```

Four results, and the last two matter as much as the first two:

- **PASS** — you observed the expected result. Not "nothing looked wrong." You *checked the specific thing the case says*.
- **FAIL** — you observed something else. Links to a bug ID.
- **BLOCKED** — you couldn't run it. Something in the way: missing data, a broken precondition, a feature that isn't reachable. Blocked is not fail, and hiding it as a pass is the single most damaging thing a tester can do.
- **NOT RUN** — you ran out of budget. Report it out loud. A suite reported as "18 passed" when 6 were never executed is a lie with good posture.

While executing, resist fixing your cases. If a case is wrong, mark it and move on; edit the suite at the end. Rewriting mid-run means you never find out how good the suite actually was.

## 2. Where scripted testing runs out (~10 min)

Your suite can only contain what you thought of on Tuesday. The bugs you didn't think of are still there, and no amount of case-writing reaches them — because the same mind that missed them while writing will miss them while executing.

**Exploratory testing** is the counterweight: simultaneous learning, test design, and execution. You are not "clicking around." You work from a *charter* — a mission for a fixed period — and you take notes as you go, so the output is reviewable work, not a vibe.

The difference from scripted testing in one line: **a scripted test asks a question you wrote down yesterday; an exploratory session lets each answer choose the next question.**

Both are necessary. Scripted cases give you repeatability and coverage you can point at. Exploration gives you the bugs nobody predicted. A tester who only does the first is a metronome; one who only does the second can't tell you what they covered.

## 3. Run a session-based exploratory session (~35 min)

Write a charter first, at `charters/CH-01.md`:

```markdown
# CH-01 — Cart survival across sessions and tabs
**Charter:** Explore the cart's persistence across login/logout, multiple tabs,
and browser navigation, to discover cases where the cart contents or totals
disagree with what the user last saw.
**Time box:** 35 minutes
**Started:** HH:MM
```

Then set an actual timer, and go. Notes go in the same file as you work — terse lines, timestamped-ish, not prose:

```
:04 added pliers x2, logged out, logged back in — cart preserved. good.
:09 two tabs. removed item in tab B, tab A still shows it. tab A "checkout" -> ?
:11 tab A checkout proceeded with the stale item. total = stale. INVESTIGATE
:16 minimized: 1 item, remove in B, checkout in A. reproduced 3/3.
:22 back button from payment step -> cart edit -> forward -> total not recalculated?
:26 couldn't reproduce the back-button one. note it, move on.
```

Three heuristics to steer with when you stall — and you will stall around minute 15:

- **The tours.** Walk the app with one lens at a time. *The money tour*: every feature that touches a price. *The variability tour*: every field a user can change. *The back-alley tour*: the least-used features, where nobody has looked. *The supermodel tour*: only what's visible — layout, alignment, truncation, currency formatting.
- **Goldilocks.** For every input: too big, too small, just right. Zero items, one item, forty items. A one-character name, a 500-character one.
- **CRUD.** For every object the app owns: can you create it, read it, update it, delete it — and what happens if you do those in a stupid order? Delete it twice. Update the thing you just deleted.

When the timer ends, stop. Write three closing lines in the charter: **what I covered**, **what I found**, **what I did not get to**. That last line is the one that makes the session reviewable by someone else.

## 4. Isolate before you report (~10 min)

You have some rough findings. A rough finding is not a bug report. Between them sits isolation, and it's most of the craft:

1. **Reproduce it.** Do it again from a clean state. Three times. If it happens 1 time in 3, that goes in the report — an intermittent bug is still a bug, and the frequency is data.
2. **Minimize it.** Strip steps until it stops happening, then put back the last one you removed. "Add 4 items, apply a filter, sort by price, log out, log in, checkout" often reduces to "log out with an item in the cart, log back in, checkout." Developers fix minimized bugs far faster, because a short repro points at a small amount of code.
3. **Vary one thing.** Does it happen with a different product? A different browser? A logged-out user? Each variation you try narrows where the defect lives, and each one you *report* saves the developer the same experiment.
4. **Get evidence.** Open DevTools (`Cmd-Option-I`) before you reproduce:
   - **Console** tab — red errors, with the file and line. Paste the text, not a screenshot of the text.
   - **Network** tab — find the request the action fired. The status code and the response body are frequently the whole story. A UI that says "something went wrong" over a `422` with a precise field-level message means the bug is in the display, not the validation.
   - A screenshot of the visible symptom, with the wrong value visible.

Try it deliberately once: open the Network tab, submit the login form with a deliberately malformed email, and read the request the app actually sends and the status it gets back. Note the status code and the response body in your charter. Whether or not that's a bug is a judgment call — but *now you can argue it with facts instead of an impression.*

## 5. Write the bug reports (~20 min)

Three bugs, one file each, `bugs/BUG-001.md` and so on:

```markdown
# BUG-001 — Checkout uses stale cart when the cart is edited in a second tab

**Severity:** Major   **Priority:** P2
**Environment:** practicesoftwaretesting.com, Chrome 141, macOS 15.5,
logged in as customer@practicesoftwaretesting.com
**Frequency:** 3 of 3 attempts

## Steps to reproduce
1. Log in as the customer account. Empty the cart.
2. Add "Combination Pliers" ($14.15). Cart shows 1 item, subtotal $14.15.
3. Open the same site in a second tab. Open the cart. Remove the item.
4. Return to the first tab (do not refresh). Click Checkout and proceed.

## Actual result
Checkout proceeds with the removed item and charges $14.15.
Network tab: POST /orders returns 200 with the removed line item included.

## Expected result
The order should reflect the server-side cart. Either the checkout is rejected
with "your cart changed," or the stale tab refreshes before payment.
**Oracle:** consistency — the cart is one object, and two views of it disagree.

## Evidence
- console: no errors
- screenshot: bugs/img/BUG-001-total.png

## Notes
Does not reproduce if the first tab is refreshed before checkout.
```

The parts people get wrong:

- **Title.** It should state the symptom and the condition in one line, so a triager can decide without opening it. "Cart bug" and "Checkout broken" are not titles.
- **Actual vs expected, separately.** Both, always. A report with only "actual" makes the developer guess your oracle, and they'll guess "works as designed."
- **Severity is not priority.** *Severity* = how bad the effect is when it happens (technical). *Priority* = how soon it should be fixed (business). A crash in an unused admin export is high severity, low priority. A typo in the checkout button is low severity, high priority — it's on the money path and everyone sees it. Confusing the two is how testers get a reputation for crying wolf.
- **Name the oracle.** Every report. It converts "I don't like this" into "this contradicts *X*," and X is arguable in a way taste isn't.
- **Report facts, not diagnoses.** "The API returns the removed item" is an observation. "The cart state isn't synced because they cache it in localStorage" is a guess, and if it's wrong, the developer will use it to dismiss the whole report. Put a guess under `## Notes`, clearly labeled, or leave it out.

If you found fewer than three real bugs, don't invent any. File what you have, and file the best **question** you found — an unspecified behavior from the state-transition work in Lesson 2 — as a report with expected result: *"undefined; requesting a product decision."* Those are legitimate output.

## 7. Journal (~20 min)

`journal/QA03.md`:

```markdown
# QA Lesson 3

## What I did
(short list)

## Scripted vs exploratory
Did your written suite or your exploratory session find the more interesting bug?
Be specific about which case or which charter minute, and say what that tells you
about how you'd split your time on a real project.

## The prediction from Lesson 2
You predicted where the first bug would be. Were you right? If not, what did the
software do that your model of it didn't allow for?

## Minimizing
Take one bug and describe what your repro looked like before you minimized it and
after. How many steps came out?

## What I don't fully understand
One specific thing — a DevTools panel, a status code you saw, the severity/priority
line — that you couldn't explain to someone else right now.
```

## What "done" looks like for QA03

- An execution log exists with a result for every case, including honest BLOCKED and NOT RUN rows
- `charters/CH-01.md` has a charter, timestamped session notes, and the three closing lines
- Three files in `bugs/`, each with severity *and* priority, actual *and* expected, a named oracle, and evidence
- At least one bug was minimized — and you can say what came out of the repro
- You read a real request in the Network tab and recorded its status code
- A QA03 journal that judges scripted vs exploratory from your own results
